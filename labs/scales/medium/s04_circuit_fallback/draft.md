# 场景 S04 · 独立草稿 —— 熔断降级

## 用户故事
> 作为**网关**，我想**下游故障时熔断并在冷却期返回降级响应**，以便**调用方得到确定答复而非超时**。

## 设计决策
1. **开态返回降级响应（Ok）而非报错（Err）**——这是"降级"与"熔断"的关键区别。
2. **降级策略可热更**：`fallback: Arc<Mutex<String>>`，`set_fallback()` 运行期更新。
3. **熔断状态**：连续失败 ≥ 阈值 → 打开 → 冷却 → 半开放行试探 → 内层恢复。
4. **直接共享类型**（usergoals）：`shared_types::ServiceReq`。

## 待测试点
- [x] 3 次内层失败 → 熔断打开。
- [x] 开态返回 Ok(降级 503) 而非报错。
- [x] 降级策略热更（503 → 200 cached）即时生效。
- [ ] 冷却后半开放行试探 → 内层恢复。

## 边界反思
- 降级响应是包装层 String（可热更）；若降级逻辑复杂（读缓存/聚合），应落运行期编译插件
  生成——fallback 字段写入 ServiceReq，插件经直接共享类型生成降级内容。
- "降级成功"计不算熔断失败（开态不触发链，metrics 不计）——观测语义。
