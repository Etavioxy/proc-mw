# 场景 S04 · 独立草稿 —— 用户查询限流

## 用户故事
> 作为 **SRE**，我想**对用户查询做每秒限流并在超时前丢弃过载请求**，以便**数据库在促销尖峰
> 期间不被读放大拖垮**。

## 设计决策
1. **上下文在共享类型**（任意类型标准）：`MicroReq.deadline_ms`（非 Ctx 字段）——deadline
   检查宿主 Thin 节点直接读请求字段，过期 → 返回码 2。
2. **链序**：OpaqueMetrics[0]（计调用）→ OpaqueRateLimiter[1]（限流）→ deadline_check[2]。
3. **配额热更**：`chain.set(1, 新限流节点)` 运行期调配额。
4. **业务零污染**：`handle_get_user(v) = v*2` 不变。

## 待测试点
- [x] 限流(1)：第 1 查放行、第 2 查被拒。
- [x] deadline 过期请求被拒。
- [x] 配额热更(1→100) 后同流量全放行。
- [x] metrics 计数 5（限流命中计入调用）。
- [ ] 限流与熔断联动（跨场景组合，见 S02/S04 small）。

## 边界反思
- 限流状态在宿主 Stateful 节点（跨热更保留）；deadline 检查是宿主 Thin（读请求字段）。
- 上下文字段（trace_id/deadline）放共享类型，而非独立 Ctx——非 i32 中心的体现。
