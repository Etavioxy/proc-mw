# 场景 S03 · 独立草稿 —— 发送失败重投 + 熔断

## 用户故事
> 作为**生产者**，我想**消费者短暂断开/积压时发送自动重投**，以便**瞬时抖动不导致消息丢失**，
> 且**持续失败时熔断保护生产者**。

## 设计决策
1. **直接共享类型**（usergoals）：消息 = `shared_types::ChannelMsg`（非 repr(C)）。
2. **发送逻辑入链**：`FlumeSendNode`（宿主 `OpaqueMw` Stateful）封装 `try_send` + 重试——
   `Full` 重试（1ms 间隔，最多 N 次）、`Disconnected` 立即失败（返回码 2）。
   发送失败以**返回码**暴露，熔断包装层可观测。
3. **链序**：OpaqueMetrics[0] → transform 插件[1] → FlumeSendNode[2]（变换先于发送）。
4. **熔断**：`CircuitBreaker::call_opaque` 包装整链——连续失败 3 次打开，开态快速失败
   （不跑链），冷却后半开放行。

## 关键实现细节
- 消费者须经**停止信号**退出（drop JoinHandle 不释放 rx）——rx 释放才触发 Disconnected。
- 熔断"开态快速失败 <10ms"证明熔断短路路径不阻塞生产者。

## 待测试点

- [x] 通道断开 → 发送失败（3/3）→ 熔断打开。
- [x] 熔断开态快速失败（Err(2)，<10ms）。
- [x] 直接共享类型（非 repr(C)）变换正确。
- [ ] 冷却后半开放行试探（熔断全周期，见 S04）。

## 边界反思
- 发送失败 = 返回码（2），经链/熔断传播——错误域收口，不 panic。
- 重试是宿主节点（Stateful，状态在宿主，跨热更保留）；插件只管变换（无状态）。
