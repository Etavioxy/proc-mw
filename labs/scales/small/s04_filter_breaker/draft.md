# 场景 S04 · 独立草稿 —— 消息过滤 + 熔断（合规）

## 用户故事
> 作为**合规**，我想**特定类别消息（如敏感 kind）在进入通道前被过滤**，且在拒绝率尖峰时
> **熔断整个管道**，以便**违规数据不出内网**。

## 设计决策
1. **直接共享类型**（usergoals）：消息 = `shared_types::ChannelMsg`（非 repr(C)）。
2. **过滤插件热更**：filter v1（拒 kind=0）→ v2（拒 kind=0/1），`chain.set` 热替换。
3. **熔断包装**：`CircuitBreaker::call_opaque`——过滤拒绝（返回码 2）→ 连续 3 次打开；
   开态快速失败（不跑链，metrics 不计）；冷却后半开放行试探 → 恢复。
4. **错误域收口**：过滤拒绝 = 返回码 2，经链/熔断传播，不 panic。

## 关键实现细节
- 熔断"打开"的判断来自链返回码（filter 拒绝），而非 panic——D7 返回码契约。
- 半开试探是熔断器自身行为（放行一次），合法 kind=2 通过 → failures 归零。

## 边界反思
- 熔断是包装层（宿主），过滤规则是插件（可热更）——"控制面在宿主、数据面可热更"的分层。
- 快速失败路径零计量（开态不跑链）——保护观测语义不被熔断污染。
