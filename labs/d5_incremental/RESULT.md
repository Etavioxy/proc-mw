# D5 编译层 · 增量失效与单态化实测

> 日期：2026-08-06 · rustc/cargo 1.94.1 · Apple Silicon
> 结构：跨 crate 真实架构（中间件独立库 + 应用 crate）· N=5000 合成核心
> 实验：`gen.sh`（生成 N 核心）→ `measure.sh`（清洁/增量计时）

## 结论

**中间件必须与 handler 分属不同 crate，且中间件接口必须非泛型——否则改中间件会触发整个依赖树重编（Θ(N)），二进制膨胀 1.5×。**

## 实测（改中间件 BODY、接口不变 → 观察依赖 crate 是否重编）

| 变体 | 干净构建 | 改中间件后增量 | 是否重编依赖 | 二进制 |
|---|---|---|---|---|
| **泛型** `Log<C_i>` | 2.99 s | **3.00 s** | `mw_generic` + **`app_generic` 全重编** | **1.28 MB** |
| **数据驱动** `Node` 链 | 2.61 s | **0.03 s** | 只有 `mw_data`，`app_data` **保持缓存** | **843 KB** |

- 泛型：`Log<C_i>` 在应用 crate 单态化，改 `Log` body → 全部实例失效重编 → **Θ(N) 增量**。
- 数据驱动：`run_chain` 非泛型、编译一份（nm 确认 `run_chain` 符号 =1），接口不变 → 依赖 crate 增量**Θ(1)**。
- 单态化膨胀：泛型二进制 1.5×（5000 份 `Log<C_i>` 实例）。

## 附带发现：同 crate 内改共享函数会整 crate 重编

初版实验把中间件和 handler 放**同一 crate**，发现改共享函数即使 body-only、`#[inline(never)]`，也会触发整个 crate 重编（CGU 粒度粗失效）。→ **设计规则：中间件必须隔离到独立 crate**，跨 crate 边界才有增量隔离。

## 对 D5 的判定

| D5 承诺 | 判定 | 证据 |
|---|---|---|
| 配置是数据不是类型（无类型级乘积） | ✓ | 数据驱动改中间件增量 Θ(1)；泛型 Θ(N) |
| 改中间件不影响全局编译 | ✓ | app_data 保持缓存（0.03s vs 3.0s） |
| 单态化体积受控 | ✓ | 843KB vs 1.28MB（1.5×） |
| 增量失效按 crate/CGU 边界 | ✓ | 跨 crate 才隔离；同 crate 粗失效（附发现） |

## 设计落点

1. **中间件放独立 crate**（如 `proc-mw` 本身），handler 依赖其接口。
2. **中间件接口非泛型**（`Node` 枚举 / dyn），杜绝 `Log<C_i>` 式的每核心单态化。
3. 这印证 CORE-CONSTRAINTS §2.5 的复杂度模型：增量 Θ(1) 不是纸面，是跨 crate 非泛型接口的实测结果。
